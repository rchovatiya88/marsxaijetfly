# Bridgehead: open-source collision, camera and GLB reference review

Primary-source web research checked September 13, 2026, alongside the current local implementation. No dependency, engine, supplied asset or runtime file was changed by this research. Main-branch versions below are the source snapshots inspected, not a claim about the latest published package. Recommendations are engineering judgments, separate from observed game acceptance.

## Decision for this candidate

Keep `fly-controls`, the resident triangle collider and A-Frame's renderer. Borrow specific verification and authoring patterns. The best immediate follow-up is a camera clearance test that covers the near-plane corners and remains correct with a parented camera. Use a version-pinned BVH only as a measured alternative broadphase if collision query or menu-build costs become a demonstrated bottleneck. Adopt Khronos validation and round-trip checks for the exported route and hero assets. Do not replace this airborne game with a walking character controller during candidate validation.

The reason is concrete: local `node_modules/aframe/dist/aframe-master.js` contains `REVISION='147'`. `package.json` separately declares `three:^0.160.0`, but `vite.config.mjs` directs gameplay imports to `window.AFRAME.THREE`. The installed r160 package/types therefore do not establish compatibility with r160 runtime APIs. The local scene uses React 18, A-Frame 1.4, a player-relative camera boom, and continuous swept sphere collision. The reference implementations must fit those facts.

## Collision patterns worth reusing

The pinned BVH character example creates position-only collision geometry using `StaticGeometryGenerator`, builds `MeshBVH`, transforms a capsule into collider-local coordinates, and uses `shapecast` with a bounding-box callback plus `closestPointToSegment` for triangle contact. It reuses scratch vectors and separates debug collision visibility from rendered art. These are useful architectural patterns. Its collision step first advances position, then corrects overlap, with five physics substeps; it explicitly leaves camera collision as a TODO. It therefore does not establish boost tunnelling resistance or camera safety. [Pinned character movement source](https://raw.githubusercontent.com/gkjohnson/three-mesh-bvh/v0.5.23/example/characterMovement.js)

For this repository, a BVH experiment should keep the current face/edge/vertex sweep as its narrowphase and use BVH bounds to choose candidate triangles. Compare results against the existing swept-sphere tests and the actual 172,065-triangle route diagnostic. Measure cold construction, warmed query cost and retained CPU data; preserve identical collision across LOD swaps. A faster ray alone is not enough to justify replacing the bike sweep. This is a proposed experiment, not an installed or validated optimization.

The official r147 FPS sample supplies another useful control: it divides the timestep into five collision steps and clamps the incoming frame delta. Its comments explicitly describe substeps as reducing the risk of missed fast crossings. This supports comparing worst-frame boost cases, not declaring discrete capsule overlap equivalent to continuous collision. [Pinned official FPS source](https://raw.githubusercontent.com/mrdoob/three.js/r147/examples/games_fps.html)

One integration trap matters for reciprocal cover: r147 `Octree.rayIntersect` calls `Ray.intersectTriangle` with backface culling enabled. Our collision surface is deliberately double-sided. Copying that ray query unchanged could make the same wall block a shot from one side but permit the reverse shot, depending on triangle winding. Retain explicit front/back tests when evaluating it. `fromGraphNode` correctly applies each mesh's world matrix and disposes temporary nonindexed geometry, which is a useful reference for the existing world-stream extraction. [Pinned Octree source](https://raw.githubusercontent.com/mrdoob/three.js/r147/examples/jsm/math/Octree.js)

## Camera and aiming patterns

`camera-controls` documents four collision rays associated with the camera near-plane corners and warns that mesh collision checks can cost performance. Its public integration uses `CameraControls.install({THREE})` and `update(delta)`. A future experiment must supply the active A-Frame Three object and update from simulation ticks, preserving pause semantics. [Official repository documentation](https://github.com/yomotsu/camera-controls)

The v2.10.1 source computes near-plane half-height from effective FOV and near distance, and half-width from aspect. This is a concrete test target for the current fixed 0.25 m camera sweep: verify that its volume protects the visible near plane at the shipped FOV/aspect. That same source writes camera position and calls `lookAt` using its own target coordinates. Our camera is nested under a yawing player and local rig, so directly adopting that controller would need explicit world/local conversion and exclusive ownership. [Pinned camera source](https://raw.githubusercontent.com/yomotsu/camera-controls/v2.10.1/src/CameraControls.ts)

Recommended bounded check: place the bike beside a court wall, sweep yaw and pitch at the widest supported aspect, draw the actual near-plane corners, and verify they stay outside resident collision while the next route marker remains readable. Preserve camera-world aiming and the physical muzzle-to-hit obstruction check. Neither an orbit camera nor a first-person direction ray alone solves third-person muzzle parallax. The latter recommendation follows the game's current camera/weapon contract; it is not a claim that the external examples implement our weapon.

`ecctrl` separates character, input, animation, camera and time APIs. Its documented `EcctrlCameraControls` wraps Drei camera controls; it is not an A-Frame adapter. Its useful pattern is the explicit state resolver and frame-driven enable/pause boundaries. Importing its controllers here would bring a different React renderer and physics ownership model. [Official API reference](https://raw.githubusercontent.com/pmndrs/ecctrl/main/docs/api-reference.md)

## GLB authoring and admission patterns

The Khronos exporter itself runs export validation and import/export round-trip comparison in its CI. Reuse that pattern for route markers, seven authored cover bodies, material resources and named Warden clips. Validate emitted files, then reimport and compare transforms and bounds before admission; source-file readability alone does not prove the actual exported collision/marker correspondence. [Exporter workflow and CI](https://raw.githubusercontent.com/KhronosGroup/glTF-Blender-IO/main/README.md)

The inspected exporter exposes `use_selection`/collection filtering, `export_extras`, `export_yup` and `export_animations`. Its `export_apply` flag applies mesh modifiers and warns about shape keys; it is not a blanket promise that every object transform is normalized. Use explicit named collections for shell/markers/proxies, store stable marker IDs in extras, and verify baked Y-up metres after export. The current main source declares Blender 5.3, so copying main into the project's installed Blender 5.2.1 would be an unjustified version change; inspect its bundled operator schema instead. [Exporter operator source](https://raw.githubusercontent.com/KhronosGroup/glTF-Blender-IO/main/addons/io_scene_gltf2/__init__.py)

Use the loader matching the active runtime. Three r147 already has `setDRACOLoader`, `setKTX2Loader`, `setMeshoptDecoder` and `parse`, but supported interfaces do not mean each decoder is installed/configured in this game. Keep the working local Draco route. Evaluate texture compression or meshopt only with decoder delivery, fallback and memory evidence. Current Three documentation lists newer extensions beyond r147; it is not the compatibility contract for this build. [Pinned r147 loader](https://raw.githubusercontent.com/mrdoob/three.js/r147/examples/jsm/loaders/GLTFLoader.js), [current loader documentation](https://threejs.org/docs/pages/GLTFLoader.html)

## What to carry forward

1. Keep one controller. The implemented flight input adapter borrows the aframe-extras-style idea of a separate input source while still feeding `fly-controls`, so keyboard, mouse and gamepad all share the existing camera/collision path.
2. Keep the present continuous collider and its actual-level tests. If profiling identifies it as costly, compare a pinned `three-mesh-bvh` broadphase under unchanged route and front/back cover tests before adding the dependency.
3. Apply exporter validation and transform round-trip checks to each new runtime GLB, while retaining the existing source-preservation and rights records.

No source code or demo assets were copied. If code is later incorporated, preserve the applicable MIT or Apache license/copyright/notice requirements from the exact pinned source. Demo model and texture rights are separate from code licenses; the owner's supplied-model rights attestation is unchanged by this review.
